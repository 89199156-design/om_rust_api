# Rust OM API Official Baseline

## Decision

Shanghai client-facing OM API will be implemented in Rust, but its weather
semantics must follow the same official Open-Meteo source baseline used by the
current Singapore production deployment.

The Rust service is an AGPL server component because the implementation is
intended to reproduce Open-Meteo server logic, not a clean-room independent
weather algorithm.

## Production Baseline

Use the Singapore production chain as the single source version:

- Singapore app path: `/opt/1panel/apps/weather_forecast_server`
- Production Docker image: `weather-forecast-openmeteo:9849315`
- Weather forecast server commit: `984931518245d1352d6ae6d8da2b889ccee6bc2a`
- Open-Meteo upstream baseline: `4efb9c49fb4a3718ed385fb22580d2e0fc56bdb2`
- Open-Meteo SDK baseline: `a29c4b62dd8445128e6db30f0a6fb5509fa1259c`

Do not mix files or behavior from other Open-Meteo versions unless this baseline
is intentionally upgraded and validated as a whole.

## What Singapore Actually Runs

The current Singapore production chain does not use the old local
`point_weather.bin` package path as the active Open-Meteo API implementation.

Observed production behavior:

- `openmeteo-api` runs from `weather-forecast-openmeteo:9849315`.
- GFS/CAMS runtime data is stored in Open-Meteo-style `.om` directories under
  `data/point`.
- WebP layers are generated by `scripts/build_webp.py` calling the local
  official API (`/v1/forecast` and `/v1/air-quality`).
- Public static WebP output is symlinked from `/opt/1panel/apps/weather/data`
  to `/opt/1panel/apps/weather_forecast_server/data/webp`.

Therefore, the Rust API must target the official Open-Meteo API behavior from
this version, not the historical Python point-package implementation.

## Behavior-Equivalent Port Rule

The Rust implementation must be behavior-equivalent to the selected Open-Meteo
source baseline for the API subset we expose. It must not substitute Open-Meteo
logic with independently designed weather algorithms, simplified heuristics, or
AI-generated approximations.

Behavior-equivalent does not mean line-by-line source translation. Rust may use
faster implementation details for indexing, caching, IO, memory layout,
parallelism, and request routing. Those implementation details are acceptable
only when the returned point values, units, field names, time windows, grid
selection semantics, and derived-variable semantics match the official baseline
within agreed tolerances.

For each supported feature, record the official source file/function used as the
semantic reference and keep the Rust behavior aligned with that source. This
applies to raw variable lookup, grid selection, DEM/elevation handling, derived
variables, units, JSON field naming, time windows, and product/model selection.

If a feature has not been behavior-ported from the baseline source and
validated, the API must fail closed with a clear error. It must not silently
serve nearest-grid, uncorrected, or approximate values under an
official-compatible parameter name.

## Rust Service Scope

The Rust service should read Shanghai-mirrored `.omranges` bundles directly and
serve the client-facing point API. It should not require Shanghai to rebuild the
full official Open-Meteo `.om` directory layout.

Initial API scope:

- GFS point forecast queries.
- CAMS point air-quality queries.
- Single point and multi-point requests.
- Hour windows suitable for current, hourly, daily-window, and route-arrival
  use cases.
- Variable subsets requested by clients.
- Derived fields needed by the product, including weather code and layer helper
  fields.

Out of scope for the first Rust service:

- Full Open-Meteo API surface.
- Every model supported by upstream Open-Meteo.
- Reimplementing Singapore WebP production in Rust.
- A closed-source proprietary weather interpretation algorithm.

## Compatibility Requirements

The Rust implementation must reproduce the Singapore baseline for these high
risk behaviors:

- `cell_selection=land` grid selection.
- DEM/elevation handling.
- `surface_pressure` and other elevation-sensitive derived variables.
- `weather_code`.
- Precipitation phase helper derived from `weather_code`.
- Thunderstorm code helper derived from `weather_code`.
- GFS 13 km and 25 km variable mixing rules used by the baseline API.
- CAMS variable names, units, and hourly windows.
- JSON field naming and units for the supported API subset.

## DEM Source Rule

When DEM or land-grid selection is needed, first copy the DEM/static grid data
from the Singapore production baseline so the Rust service uses the same
versioned source as the official Open-Meteo deployment.

If the Singapore DEM is not suitable for the Rust implementation because of
format, resolution, projection, coverage, or version mismatch, do not invent a
separate DEM source on Shanghai. Download a new compatible DEM package through
the Silicon Valley download server, verify it against the Open-Meteo baseline,
and then mirror the verified package to Shanghai.

Until that DEM path is implemented and validated, the Rust API must reject
`cell_selection=land` instead of silently serving nearest-grid results.

## Version Upgrade Rule

When Open-Meteo is upgraded, treat it as a single baseline replacement:

1. Upgrade Singapore/test official container first.
2. Record the new Open-Meteo upstream commit and SDK commit.
3. Run point-level comparison against the old baseline and public reference.
4. Port the changed logic into Rust.
5. Run Rust-vs-official comparison before production rollout.

Do not cherry-pick individual official source files from multiple upstream
commits.

## Validation

Use the Singapore production deployment only to lock the Open-Meteo source
version. Do not treat Singapore API output as the final correctness oracle,
because its validation is not complete.

Final correctness must be validated against the official Open-Meteo API for
matching model/run/time/point/variable cases whenever the official API exposes
the required request shape. Singapore can still be used as a diagnostic
comparison target to isolate whether a mismatch comes from our Rust port or from
the Singapore deployment.

Minimum validation set:

- Same point, same run, same hour window, same variables.
- Coastal points, inland points, high-elevation points, desert/western China,
  South China coastal, and Xinjiang timezone-relevant points.
- Weather-code-sensitive cases: rain, snow, freezing rain, fog, thunderstorm,
  clear/cloudy transitions.
- Route-style multi-point queries with dozens of points.
- CAMS point queries for PM2.5, PM10, aerosol optical depth, dust, and the
  variables kept in production downloads.

The Rust service is acceptable only after key outputs match the official
Open-Meteo API within agreed tolerances, with any unavoidable differences
documented by variable and cause.
